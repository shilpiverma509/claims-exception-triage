Four things worth knowing before we start.

1 · the problem

The hard part isn't fixing the claim.
It's working out why it's stuck.

  • Most claims process automatically. When one can't, it drops into the exception queue — a holding list for claims that need a person.
  • Every claim there carries a pend code — a short system code meant to say why it stopped, like an error code. In practice it's often generic: "needs review," not what to review.
  • So an analyst opens it, reads the note — a free-text comment a person typed the last time someone looked at this claim — then manually logs into a few separate lookup systems to confirm what's actually wrong: was there a prior authorization on file, has this claim come through before, is there a contracted rate for this procedure. Nothing pulls those answers together automatically.

And the order is wrong

The exception queue is worked oldest-first, not worst-first.

An overdue $42,000 claim can sit behind a $45 claim that simply arrived earlier — illustrative, not a measured rate.

2 · the pipeline, part 1 — offline, no model

First, the sample data is generated.

generate_data.py

Seeded random generator producing 75 synthetic claims — 50 into dev_claims.json for practice, 25 sealed into eval_claims.json — each with a matching ground-truth label. Assigns pend codes P10–P16 one-to-one with the 7 root causes, plus generic codes that carry no signal, plus deliberate "trap" claims where the note implies one cause and the evidence says another.

generate_mock_systems.py

Generates the 3 mock source systems — prior-auth registry, claim history, contract rates — including the planted contradictions the trap claims above depend on.

make data — runs once, offline, no LLM involved at all.

The difficulty of every claim in this project was authored, not observed — this is exactly why the disclaimers on slide 2 matter more than usual here.

Then each claim runs eight steps. Only one is the model.

5 · the trust design

"The model proposes. Code disposes.
A human approves."

  • The guard — a separate block of plain, ordinary code that runs right after the AI answers — can only make the system more cautious: raise the urgency score, or force a human to look. It never relaxes anything the AI said.
  • The AI is blocked at the code level from sending a claim to a human reviewer itself; only the guard can do that.
  • Nothing executes automatically. No claim is paid, denied, or adjusted by the system — every action still waits on a person.
20 seconds. This is the line that matters most in the whole deck — say it slowly, then move on.

A Streamlit app. Every click writes one line to the log.

Approve

One click, no extra input by design — friction here suppresses the very corrections the loop needs. Writes human_decision: approve to the audit log. Counts toward calibration only; it is never treated as a confirmed-correct label.

Reject / Reassign

The analyst also picks the actual root cause from the same fixed 7-item list the AI uses (or "none of these fit"). The correct team is derived from that cause automatically — an analyst can't create a pairing the guard would forbid either. Writes the correction to the audit log.

Either way: nothing executes. No claim is paid, denied, or reassigned in any real system — the click only appends one row to outputs/audit.jsonl. The second tab, Audit Trail, is that same log rendered as a searchable table — every ingest, redaction, AI call, guard override, and human decision, filterable by claim.

30 seconds. Point at the two buttons and say the sentence plainly: "approve writes a row, reject writes a row — the row is the entire effect." That's the whole point of this slide.

9 · feedback loop — when it runs, and what comes out

Not automatic. Not continuous. Run on purpose.

Someone runs make feedback after a batch of Reject/Reassign clicks has piled up in the audit log from slide 10 — nothing fires on a schedule or after a single click. It reads every correction since the last run and turns it into three things:

A permanent test case

Only if the analyst's cause differs from what the AI said. Saved as a labeled example the test suite checks against — so if a future prompt change breaks this same claim again, make test catches it.

A confidence check

How often a correction happens, grouped by how confident the AI was at the time. This suggests a new confidence cutoff for forcing human review, and states its cost in extra escalations — it never applies the change itself.

Prompt material

Repeated "said X, actually Y" patterns and draft worked examples, written to a report for a person to read and, by hand, fold into the next version of the AI's instructions.

An approval is not a label. A rejection costs the analyst effort and carries information; an approval might just mean someone clicked through forty claims. So only corrections teach the system anything — approvals just get counted, never treated as "confirmed correct."

The output is a markdown report in outputs/, read by a person. Nothing retrains and no prompt file changes until that person edits prompts.py themselves — the loop closes through a reviewed release, never silently.

35 seconds. This directly answers "when does feedback happen" — say the command out loud, then the three outputs, then land on "a person edits the prompt file — nothing retrains itself."
10 · close — the next iteration

The next iteration isn't a rebuild — it's feedback, running.

Fix the one prompt line that caused the sealed-set miss, then let the loop from the last slide do the rest. Every real correction can become a confusion pair — a repeated pattern where the system keeps saying cause X when the real answer is Y. That pattern is a prompt problem, not a one-off mistake — and it's exactly the kind of edge case synthetic data can't surface, because I already know what my own synthetic data looks like. Enough pairs on the same two causes becomes the material for a new prompt version, drafted by hand from real cases, evaluated on the dev set before it's trusted, frozen only if it actually beats the current one. Real edge cases in, a sharper prompt out — never automatic, never silent.

The one thing that doesn't change once any of that happens: a human approves every action. That's not a limitation — that's the product.
